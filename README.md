# zkcredit — Layer 3: Zero-Knowledge Threshold Verification

Prototype built in the research chat, benchmarked, and handed over for integration into the main dissertation repo. See `HANDOVER.md` task **T2**.

## What it proves

> *"I know a credit score S and salt r such that `Poseidon(S, r) == C` (the commitment anchored on the consortium ledger) **and** `S >= T` (the lender's threshold)"* — without revealing S or r.

- **Private inputs:** `score`, `salt`
- **Public inputs:** `commitment`, `threshold`
- **Lender learns:** one bit. Not the score, not the margin above threshold, not a single behavioural feature.

## Quick start

```bash
npm install
./setup.sh        # installs circom, compiles circuit, runs trusted setup ceremony
node bench.js     # end-to-end flow + benchmarks + negative tests
```

`setup.sh` takes ~2 minutes, dominated by the powers-of-tau phase 2 preparation.

## ⚠ Before re-running setup

Delete `build/verification_key.json` and `build/verifier.sol` first. They are artefacts of the *original* ceremony. `setup.sh` generates fresh entropy and a different proving key — the shipped verification key will not match it, and proofs will fail verification with an unhelpful error. Regenerate both.

## Three design decisions that are load-bearing

**1. Poseidon binding.** Without it, a borrower proves only "I know *some* number ≥ T", which is worthless. Binding to the on-chain commitment proves it is *the* score the ML layer computed and the consortium ledger anchored. This constraint is the seam joining Layer 3 to Layers 1 and 2. Do not remove it.

**2. `ge.out === 1` is a hard constraint, not an output flag.** An ineligible borrower cannot generate a proof at all. The existence of a valid proof *is* the attestation — there is no "false" proof to leak information.

**3. `Num2Bits` range checks on both comparator operands.** Without them a malicious prover supplies `score = p − k` — a huge field element that behaves like a negative number under modular arithmetic — and defeats the comparator entirely. Known ZK footgun; the checks are not optional.

## Correctness tests in `bench.js`

| Test | Expected |
|---|---|
| Eligible borrower (742 vs 600 / 700 / 742) | Proof generated and verified |
| Ineligible borrower (742 vs 800) | Generation **fails** — `ge.out === 1` unsatisfiable |
| Forged score (claims 950 against real commitment) | Generation **fails** — Poseidon binding violated |

All three must pass. Different behaviour is a correctness regression.

## Known open issue

**Binary-search leak.** A lender issuing repeated proof requests at descending thresholds can recover a borrower's exact score in ~10 queries, defeating the privacy guarantee. Mitigation options under discussion on the research side: nonce-binding, rate limiting, or coarse threshold bands. Tracked as Open Research Question 1 in `HANDOVER.md`. Do not build the integration layer without resolving this.
